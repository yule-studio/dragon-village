# 브랜치 전략

## 0. 대원칙

1. **모든 비사소한 작업은 GitHub Issue 에서 시작한다.** 코드를 건드리기 전에 이슈부터 만든다.
2. **이슈 번호 없는 브랜치는 금지한다.** 이미 만들었다면 이슈를 만들고 이슈번호 브랜치로 재정리한다.
3. `main` · `release` · `dev` 에는 **직접 commit / push 금지.** 항상 작업 브랜치 → PR.
4. **force-push · admin bypass · 자동 merge 금지.** 사람 승인 없이 하지 않는다.

## 1. 영구 브랜치

| 브랜치 | 역할 | 머지 출처 | 배포 |
| --- | --- | --- | --- |
| `main` | 운영. 항상 배포 가능한 상태 | `release`, `hotfix/*` | 태그 기준 릴리스 |
| `release` | 출시 준비 · 안정화 · QA | `dev` | 스테이징 |
| `dev` | 통합. 기본 브랜치 | 작업 브랜치 | 개발 |

```
작업 브랜치 ──PR──▶ dev ──PR──▶ release ──PR──▶ main
                                                  │
                          hotfix/* ◀──분기────────┘
                              └──PR──▶ main + dev (양쪽 반영)
```

- `dev` 가 **기본 브랜치**다. PR 의 base 는 특별한 사유가 없으면 `dev`.
- `release` 는 출시 묶음을 고정하는 용도다. 여기서는 **버그 픽스만** 받는다. 새 기능은 `dev` 로.
- `main` 머지 시 **버전 태그**를 단다: `v0.3.0`.

## 2. 브랜치 이름 규칙

```
<이슈번호>-<프리픽스>-<수정할-내용>
```

- 전부 **소문자 kebab-case**
- 예:
  - `12-feat-mcp-run-loop-tool`
  - `27-fix-highbrow-login-detection`
  - `31-docs-branch-strategy`
  - `44-refactor-extract-dragon-config`

### 프리픽스

| 프리픽스 | 용도 |
| --- | --- |
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `docs` | 문서 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `test` | 테스트 |
| `chore` | 빌드 · 의존성 · 잡무 |
| `infra` | CI · 배포 · 인프라 |
| `design` | UI · 화면 |

### 예외

`hotfix/<이슈번호>-<설명>` 만 `main` 에서 분기한다. 운영 장애 대응 전용이며,
머지 후 반드시 `dev` 에도 반영한다.

## 3. Issue

작업 시작 전 아래를 채운다.

- **배경(Background)** — 왜 필요한가
- **목표(Goal)** — 무엇이 되면 끝인가
- **범위(Scope)** / **비범위(Non-goals)**
- **완료 조건(Acceptance)** — 검증 가능한 형태로

라벨로 프리픽스(`feat`/`fix`/…)를 붙여 브랜치 이름과 맞춘다.

## 4. PR

- **제목**: `[Type] 요약 (#이슈번호)` — 예) `[Feat] MCP run-loop 도구 추가 (#12)`
- **본문**: 연결 이슈(`Closes #12`) · 요약 · 변경 사항 · 검증 방법 · 리스크
- **UI 변경이면 before/after 스크린샷 필수**
- **머지는 merge-commit 전용** (squash 금지), 머지 후 브랜치 삭제
- green CI · 리뷰 · Acceptance 확인 후에만 머지

## 5. 이 저장소 특유의 주의

- **자동화 스크립트는 실기기를 조작한다.** 동작을 바꾸는 PR 은
  실제 1사이클 이상 돌려본 로그를 검증 항목에 첨부한다.
- **안전장치 코드는 임의로 완화하지 않는다.**
  `dvguard.py` 의 계정삭제 금지구역, `dvloop.py` 의 하이브로 로그인 2중 검증은
  약화하는 변경일 경우 PR 본문에 사유와 대체 안전장치를 명시해야 한다.
- **계정 자격증명은 절대 커밋하지 않는다.** 키체인에서만 읽는다.
